How to read this table

Each row shows a single rule and how it fared against this model. The columns trace what happened, left to right:

  1. In model — count of elements of the rule's target class present in the IFC (e.g. 146 IfcSpace entities).
  2. Selected — of those, how many also matched the rule's property filter (e.g. SpaceType=Corridor). When this drops below "In model", the cell is highlighted — the difference is filtered out by the property filter, not missing.
  3. Pass / Fail / Inc / Hum / Uns — what verdict the rule gave each Selected element. When State is not applicable, any non-zero number here is a single class- or model-level marker (rendered italic with ᵃ), not per-element verdicts.
  4. State — whether the rule actually ran on real elements:
  • evaluated — produced at least one per-element verdict.
  • not applicable — selector matched nothing (In model or Selected was 0). A single class-level marker may be emitted to flag a data tagging gap.
  • skipped — produced no result at all this run.
  • stage-filtered — deferred until a later design stage, not run now.

The four headline metric cards above (Rules in pack / evaluated / not applicable / skipped) are the rule-axis rollup of the State column. Elements checked is the count of distinct elements the rule pack actually verdicted.

Waivers and Deviations

Waivers are accepted deviations attached to FAIL results. The status never flips — a waived FAIL stays FAIL, with the waiver shown as evidence. An invalid waiver is no longer in force (past its expiry date, rule version changed, occasion exhausted, or identity mismatch). A superseded waiver is one whose underlying check now passes, so the waiver no longer applies.
